# DiaVision Client Documentation

## Purpose
DiaVision is a web-based diabetes screening experience. It guides a user through a short multi-step questionnaire, validates the answers, runs a diabetes risk prediction, and presents the result as a clear visual report with supporting explanations and next-step guidance.

The current version is built around the supplied Python Pima-based logistic model. In production, the web app does not execute Python directly. Instead, it uses a server-side TypeScript implementation of the same model logic and shared model parameters, with the option to forward requests to a separate external prediction API later.

## What The Product Does
From a client perspective, the product provides:

- A polished landing page that explains the screening tool and its purpose.
- A guided six-step intake flow instead of one long form.
- Validation for each input before a result is requested.
- A server-side prediction route so secrets and provider configuration do not live in the browser.
- A final result view with:
  - estimated probability
  - low / moderate / high risk band
  - contributor explanations
  - recommended next actions
  - provider and disclaimer information

## What The Product Does Not Do
This project currently does not include:

- user accounts
- a database
- stored assessments or patient history
- analytics dashboards
- clinician workflow tooling
- direct electronic medical record integrations
- a live Python API server in the deployed web app

All prediction requests are handled in memory at request time. The app behaves like a screening experience, not a patient records system.

## User Journey
The visible user flow is:

1. The user lands on the homepage and sees a short explanation of the product.
2. The user starts a step-by-step assessment.
3. The wizard collects the exact model inputs:
   - `pregnancies`
   - `glucose`
   - `bloodPressure`
   - `skinThickness`
   - `insulin`
   - `bmi`
   - `diabetesPedigreeFunction`
   - `age`
4. The user reviews the values before submission.
5. The browser sends the validated payload to the internal route `POST /api/predict`.
6. The server validates the payload again and computes a prediction.
7. The result page shows the visual gauge, summary, contributors, recommended actions, and disclaimer.
8. The user can edit answers or start over.

## End-To-End Technical Flow
The runtime flow is:

1. `app/page.tsx` renders the landing page and mounts the form.
2. `components/risk-assessment-form.tsx` manages the multi-step wizard in the browser.
3. The form uses `react-hook-form` with `zod` validation from `lib/validation.ts`.
4. On submission, the browser sends `{ input: ... }` to `app/api/predict/route.ts`.
5. The route validates the body again with `predictionRequestSchema`.
6. The route calls `generatePrediction()` from `lib/prediction-client.ts`.
7. `lib/prediction-client.ts` decides between:
   - embedded model mode if `PREDICTION_API_URL` is not set
   - external provider mode if `PREDICTION_API_URL` is set
8. Embedded mode calls `buildEmbeddedPrediction()` in `lib/risk-engine.ts`.
9. External mode forwards the request to the configured provider, then normalizes the provider response with `normalizeExternalPrediction()`.
10. The normalized `PredictionResult` is returned to the browser.
11. `components/result-card.tsx` and `components/risk-gauge.tsx` render the final experience.

## Architecture Summary
The project is intentionally simple and split into clear layers:

- `app/`: Next.js application shell, page entry points, API route, global styling.
- `components/`: UI building blocks and the multi-step assessment wizard.
- `lib/`: validation, prediction routing, embedded model logic, and shared utilities.
- `types/`: shared TypeScript interfaces for requests and results.
- root files: project configuration, environment examples, standalone Python model script, and high-level docs.

## Prediction Logic Explained In Plain Language
The current prediction system works in three major stages.

### 1. Input collection
The app collects the eight measurements required by the supplied model. This is important because the current UI is not estimating or inventing missing clinical factors from unrelated lifestyle questions.

### 2. Embedded model calculation
When the embedded predictor is used:

- some fields can be treated as missing and replaced with training-set medians
- all features are standardized using saved scaler statistics
- a logistic-regression equation calculates the base probability
- a Frank copula adjustment adds an extra glucose/BMI interaction signal
- the result is clamped into a usable 0.01 to 0.99 range

### 3. Result explanation
After computing the probability, the engine:

- assigns a risk band:
  - below `0.25` -> `low`
  - `0.25` to below `0.55` -> `moderate`
  - `0.55` and above -> `high`
- selects the strongest positive drivers
- writes human-readable summary text
- generates recommended actions

## External Provider Mode
The app can be switched from embedded mode to external mode by setting `PREDICTION_API_URL`.

In that case:

- the same validated payload is posted to the external endpoint
- optional auth headers are added from environment variables
- the response is normalized into the internal `PredictionResult` shape
- the UI remains the same even if the provider changes

This means the client can swap the prediction backend later without redesigning the user interface.

## Standalone Python Script
`diabete_risk_predictor.py` exists for portability and validation of the model outside the web app.

Its role is:

- provide a standard-library-only Python version of the model
- mirror the shared coefficients and preprocessing rules
- allow local CLI testing
- serve as a reference implementation alongside the TypeScript engine

Important distinction:

- the deployed web app uses the TypeScript prediction path
- the standalone Python file is a companion tool, not a web-server dependency

## Validation And Error Handling
The project validates data in two places:

- in the browser before submission
- on the server after submission

This double-validation pattern reduces accidental bad input and protects the backend route.

Common handled errors include:

- invalid or missing JSON
- out-of-range numeric values
- provider timeouts
- external provider failures
- unexpected server errors

User-facing errors are intentionally written in plain language rather than raw stack traces.

## Data Handling And Privacy
Current data behavior is intentionally minimal:

- no database is used
- answers are not persisted by the app
- the browser keeps answers in component state until submission
- prediction requests go to the internal API route
- if an external provider is configured, the server forwards the validated payload there
- API keys remain server-side

From a client-scope perspective, this project is a screening UI and prediction service wrapper, not a patient-data platform.

- short step-by-step intake instead of a long medical form
- strong mobile support
- dedicated result page instead of a tiny inline result card

- the public site is a standard Next.js App Router application
- the prediction entrypoint is an internal API route

- demos
- internal previews
- client reviews
- staged rollout before a separate model API is available

## Current Limitations And Client Considerations
The client should understand these constraints clearly:

- The model is educational and screening-oriented, not diagnostic.
- The embedded predictor mirrors the supplied model, including its dataset assumptions and limitations.
- `diabetesPedigreeFunction` is technically correct for the source model but is not naturally user-friendly for most end users.
- There is no persistence, reporting, or history tracking yet.
- There is no clinician portal or workflow layer.
- There is no audit logging or consent-management workflow yet.
- If a regulated or clinical-production product is desired, additional medical, legal, and product work is required beyond this repository.

## Bottom Line
DiaVision is currently best understood as:

- a polished client-facing screening UI
- a server-side prediction adapter
- an embedded implementation of a supplied Python diabetes-risk model
- a good foundation for future integration with a dedicated model API or broader healthcare product features
